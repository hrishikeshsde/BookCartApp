# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

BookCart is an online book store: an ASP.NET Core Web API (.NET 10, EF Core 10, SQL Server) in `BookCart/` hosting an Angular 22 SPA in `BookCart/ClientApp/`. Both live in one project (`BookCart.csproj`) wired together with `Microsoft.AspNetCore.SpaProxy`.

## Commands

Build layout: the solution is `BookCart.slnx` at the repo root (Visual Studio 2022 17.13+ or the CLI). `global.json` pins the .NET SDK (10.0.x). `.editorconfig` records the code style; `dotnet format BookCart.slnx --verify-no-changes` must stay clean (CI runs it). `Directory.Build.props` sets `TargetFramework` (net10.0), nullable and implicit usings for every project. `Directory.Packages.props` holds all NuGet versions (central package management): project files reference packages without a `Version`, so change versions there.

Backend (run from `BookCart/`):
- `dotnet build`: the first Debug build runs `npm ci` in `ClientApp/` automatically if `node_modules` is missing. `ClientApp/.npmrc` sets `legacy-peer-deps` (Bootstrap peers on `@popperjs/core`, which this app does not use); delete it when Bootstrap is removed in F6.
- `dotnet run --launch-profile BookCart`: starts the API at https://localhost:7073. SpaProxy then runs `npm start` and serves the Angular dev server at https://localhost:53424.
- `dotnet publish -c Release`: the `PublishBuildClient` target runs `npm ci` and `npm run build -- --configuration production`, then copies `dist/` into `wwwroot` (without `prerendered-routes.json`; the XML documentation file is not published either).
- One-click Windows scripts are in `scripts/` (`dev-start-all.bat` for development with SQL Server in Docker, `release.bat` for a production release with Docker Compose from `deploy/`; see README). Publish `BookCart/BookCart.csproj` explicitly: a solution-level publish also builds the test project.
- `dotnet publish -c Release -t:PublishContainer`: builds the Linux image `bookcart` with the SDK (non-root user, HTTP on 8080, no Dockerfile). Add `--os linux --arch x64 -p:ContainerArchiveOutputPath=<file>.tar` to write a tar archive instead of needing a Docker daemon. Container settings are in the README.

Frontend (run from `BookCart/ClientApp/`):
- `npm start`: runs `ng serve` on port 53424 over HTTPS, using the ASP.NET dev cert (the `prestart` step runs `aspnetcore-https.js` to generate it).
- `npm run build`
- `npm test`: runs the Vitest unit tests once in jsdom (no browser; `npm run test:watch` re-runs on change). To run one spec file: `npm test -- --include src/app/services/token-storage.service.spec.ts`. Use Vitest's `vi.useFakeTimers()` for time, not `fakeAsync` (it needs a zone ProxyZone that Vitest does not set up). Store specs use the real store with `HttpTestingController` (stores that follow the session are driven through `AuthStore` and `TestBed.tick()`); component specs fake the stores with `src/app/testing/fake-stores.ts` and `fake-books-store.ts`.
- `scripts/smoke` is a Chrome click-through of the real app (browse, guest cart, register, login, checkout, wishlist, admin, session expiry); see `docs/FRONTEND_CHANGES.md` for how to run it.

Backend tests (run from the repo root): `dotnet test BookCart.Tests -c Release`. Prefer `-c Release`: a Debug build of `BookCart` also installs the client's packages, which the tests do not need. The tests host the real API on a throwaway LocalDB database `BookDB_Test` that `ApiFactory` drops and rebuilds with the real migrations on every run; the migration/upgrade/schema tests use further scratch databases (`BookDB_Test_*`, dropped afterwards). Set `BOOKCART_TEST_DB` to use another SQL Server, and never point it at a real database.

There is no frontend lint configuration. CI (`.github/workflows/ci.yml`) runs the format check, a warnings-as-errors build and the tests against a SQL Server container (`BOOKCART_TEST_DB`), the Angular unit tests (Vitest) and production build, and builds the image archive.

## Setup prerequisites

- The database schema is defined by EF Core migrations (`BookCart/Migrations`), not by `DBScript/BookDB.txt` (kept as the legacy script that created every existing database). New database: create an empty one and run `dotnet tool restore` then `BOOKCART_EF_CONNECTION="<conn string>" dotnet ef database update --project BookCart`; the migrations also insert the user types and categories. **Existing database** (created from the old script): back it up, run `DBScript/B4_adopt_migrations.sql` once, then apply the migrations; `docs/BACKEND_CHANGES.md` (section B4) has the full procedure, what the cleanup does to old data, and when it stops. No admin account is seeded: register a user in the app, then promote it with `UPDATE UserMaster SET UserTypeID = 1 WHERE Username = '<username>'`.
- Passwords are stored as ASP.NET Identity hashes in `UserMaster.PasswordHash` (`Services/PasswordService.cs`). The legacy plaintext `Password` column is only read to upgrade old rows on their next login, then nulled. A database older than that needs `DBScript/B0.2_password_hash.sql` run once, before the migrations are adopted.
- Secrets are not stored in `appsettings.json` (the committed values are blank, and startup fails fast if they are missing). In development set them with user-secrets from `BookCart/`: `dotnet user-secrets set "ConnectionStrings:DefaultConnection" "<conn string>"` and `dotnet user-secrets set "Jwt:SecretKey" "$(openssl rand -base64 48)"` (min 32 chars). In other environments use the `ConnectionStrings__DefaultConnection` and `Jwt__SecretKey` environment variables or a vault. The old key that was committed to git history is compromised and must never be reused.
- Book summaries (`POST api/book/{id}/summary`) are generated by the API calling Google Gemini; the key never reaches the browser. It is optional: set `Gemini:ApiKey` (user-secrets in development, or the `Gemini__ApiKey` environment variable); without it the endpoint answers 503. `Gemini:Model`, `Gemini:CacheDays` (default 7) and `Gemini:TimeoutSeconds` are also configurable.

## Architecture

### Backend (`BookCart/`)

- The model is maintained by hand and the schema is changed only through migrations: edit the entity classes (columns) or `Models/BookDBContext.Schema.cs` (relationships, unique indexes, check constraints, column types), then `dotnet ef migrations add <Name> --project BookCart --configuration Release` and review the file. `BookDBContextFactory` lets `dotnet ef` run without the web host or secrets (`BOOKCART_EF_CONNECTION`, else the local `BookDB_Dev`). A test fails if the model and the migrations disagree. A migration that changes existing data needs the care `SchemaHardening` took: merge or delete only what could never have been valid, stop with a clear message for anything needing a decision, and keep it all in one transaction.
- Startup layout: `Program.cs` is five lines; the wiring lives in `Extensions/` (`AddBookCartOptions`, `AddBookCartPersistence`, `AddBookCartAuth`, `AddBookCartApi`, and `UseBookCart` for the ordered request pipeline: read its comments before reordering middleware).
- Request flow: `Controllers/` → `Services/I*Service` → `BookDBContext`. Each service is an interface plus its implementation in one file under `Services/` (`BookService`, `CartService`, `WishlistService`, `OrderService`, `UserService`, `TokenService`, `GeminiBookSummaryService`, `CoverStorage`, `PasswordService`), registered as scoped in `PersistenceExtensions`/`AuthExtensions`. Everything is async and takes a `CancellationToken`. Controllers return DTOs from `Dto/` (`BookDto`, `CartItemDto`, `OrderDto`…), never entities, and use `TimeProvider` for time. Controllers derive from `ControllerBase` with `[ApiController]` (automatic 400 with the invalid fields listed). The solution builds with warnings as errors (`Directory.Build.props`).
- Configuration is typed options in `Options/` (`JwtOptions`, `DatabaseOptions`, `StorageOptions`, `RateLimitingOptions`, `SecurityOptions`), validated at startup: the app refuses to start and lists every invalid setting. Do not read `IConfiguration` keys directly. The cover default lives at `Storage:DefaultCoverImageFile` (it used to be the root key `DefaultCoverImageFile`). Two optional settings exist for containers: `Storage:UploadFolder` (covers are stored in and served from this folder instead of `wwwroot/Upload`; the default cover still falls through to `wwwroot/Upload`) and `Security:DataProtectionKeysPath` (the Data Protection keys that encrypt the guest cookie live there, so guest sessions survive a restart). Mount a volume writable by the container user on each.
- Errors: throw `NotFoundException`, `BadRequestException` or `ConflictException` (`Errors/`); `ApiExceptionHandler` maps them to 404/400/409 ProblemDetails and everything else to a logged 500 with no details. Bodiless 401/403/404/429 responses also get a ProblemDetails body (`UseStatusCodePages`).
- The DbContext is pooled and retries transient SQL failures (`EnableRetryOnFailure`), so any code that opens its own transaction must run inside `Database.CreateExecutionStrategy().ExecuteAsync(...)` and clear the change tracker at the start of each attempt (see `OrderService.CreateOrderAsync` and `CartService.MergeAsync`). `BookDBContext` has a single options constructor (required for pooling). The database enforces uniqueness, relationships and value rules (see `docs/BACKEND_CHANGES.md`, section B4), so concurrent requests can collide: `CartService`/`WishlistService` catch the unique-index violation (`DatabaseErrors`) and carry on with the winner's row. Order lines have deliberately no foreign key to `Book` (history outlives the book); deleting a book removes it from all carts and wishlists by cascade.
- `GET api/book` and `GET api/book/GetCategoriesList` are output-cached for 5 minutes under the `catalog` tag; admin add/update/delete evicts it. Authenticated requests are never cached. `GET api/book/search` (page, pageSize, category, search, minPrice, maxPrice) pages and filters in the database and is not cached. Responses are gzip/brotli compressed (not over HTTPS). `GET /health` (public) is unhealthy when the database is unreachable or has pending migrations. Unknown `/api/...` routes are 404, not the SPA shell.
- No URL carries a user id. Who is calling comes from `ICurrentUser`: the signed-in user (id from the validated JWT), or else an anonymous guest (id from the encrypted guest cookie). Cart endpoints (`api/shoppingcart`, `items/{bookId}`, `count`) work for both; wishlist, orders and checkout need a login; a request cannot name another person's data because there is nothing to name. Reading never creates rows: a cart or wishlist is created by the first book added.
- Checkout (`POST api/checkout`) ignores the request body: `OrderService.CreateOrderAsync` prices the order from the `Book` table and the server-side cart, claims (deletes) the cart rows and writes the order in one transaction, and returns `{ orderId }`. It returns 409 when there is nothing to check out, including a concurrent double-submit. Order dates are UTC.
- Secure by default: `Program.cs` sets a fallback authorization policy, so every endpoint requires a signed-in user unless it has `[AllowAnonymous]` (login, register, username check, book reads, `POST api/guest`, guest-capable cart actions) or its own `[Authorize]`. Do not put `[AllowAnonymous]` on a class that also holds `[Authorize]` actions: it overrides them. The SPA fallback route is explicitly `.AllowAnonymous()`.
- Guest carts: the first book an anonymous visitor adds starts a guest session by itself (`IGuestSession`): a server-generated id (>= 1,000,000,000) in an encrypted HttpOnly `bc_guest` cookie (Data Protection), valid for 30 days. A forged or expired cookie is treated as no cookie. `POST api/guest` also starts one explicitly. Logging in merges the guest cart into the user's (quantities add) and removes the cookie; a failed login does neither.
- Auth: `LoginController` issues an HS256 JWT (`TokenService`) valid for `Jwt:ExpiryMinutes` (default 60; there is no refresh flow yet). `sub` and `userId` are the user id, and the role ("Admin" or "User") is the `ClaimTypes.Role` claim (key `http://schemas.microsoft.com/ws/2008/06/identity/claims/role`). The only named policy is `UserRoles.Admin` (`AuthExtensions`), applied with `[Authorize(Policy = UserRoles.Admin)]`. User types are the seeded ids in `UserTypeIds`.
- `BookController` POST/PUT take `multipart/form-data` with one field per book property (`bookId`, `title`, `author`, `category`, `price`, validated by `BookForm`) and an optional cover image in `file`; POST answers 201 with the saved `BookDto`, PUT 200 with it, DELETE 204. `Services/CoverStorage.cs` owns the file handling: only `.jpg/.jpeg/.png/.webp` up to 2 MB whose content matches the extension, saved as `<guid>.<ext>` in `wwwroot/Upload/` (the client's file name is never used); a bad file is a 400. If no file is sent, a new book gets `Storage:DefaultCoverImageFile`, and an update keeps the stored cover. The old file is deleted when a cover is replaced or the book is deleted (never the default). Uploaded covers are git-ignored; only `Default_image.jpg` is tracked.
- API documentation is Development only: the OpenAPI document at `/openapi/v1.json` (built-in `AddOpenApi`, Microsoft.OpenApi 2 types in `Microsoft.OpenApi`) and the Scalar UI at `/scalar/v1`. Endpoints are marked as requiring the Bearer scheme unless they have `[AllowAnonymous]`. JSON is System.Text.Json only.
- Rate limits (per client IP, fixed 1-minute window): login and registration share the `auth` policy (`RateLimiting:AuthPermitLimit`, default 10); the signup username check uses `lookup` (`RateLimiting:LookupPermitLimit`, default 30); book summaries use `summary` (`RateLimiting:SummaryPermitLimit`, default 5, each uncached one is a paid AI call). Over the limit is 429 with `Retry-After`. Behind a reverse proxy configure forwarded headers, or every caller shares the proxy's address.
- Every response, including errors, carries `X-Content-Type-Options`, `X-Frame-Options` and `Referrer-Policy`, plus a Content-Security-Policy that is **report-only** until `Security:EnforceCsp` is `true` (it has not been checked against the built SPA yet: check the browser console for violations first; `/scalar` is exempt). Requests that match no endpoint, or the SPA shell asked for under `/api`, get 404 before authorization (the fallback policy would otherwise make them 401). The SPA fallback answers GET/HEAD only, so other methods on unknown routes get 405.
- Logging: default level is Information; orders placed, admin book changes, logins, failed logins and rate-limit hits are logged (never passwords or tokens).

### Frontend (`BookCart/ClientApp/src/app/`)

- The app is all standalone components with no NgModules. `main.ts` bootstraps with `provideRouter`, `provideHttpClient(withXhr(), withInterceptors(...))`, `withComponentInputBinding()`. The app is zoneless (`provideZonelessChangeDetection()`, no zone.js, no polyfills file): every component is `OnPush` and changes only through signals, inputs, events or the async pipe, so never mutate a plain field in an async callback. It still uses XHR instead of Angular 22's fetch default until F6.
- Components are split smart/dumb. Smart ones (route pages: `home`, `book-details`, `nav-bar`, `login`, `checkout`, `manage-books`, `my-orders`, `book-form-page`...) inject the stores they need, read their signals and call their methods. Dumb ones (`book-card`, `book-filter`, `price-filter`, `search`, `addtocart`, `addtowishlist`, `similarbooks`, `book-summary`, `book-form`) only have `input()`/`output()` and never inject the store. Route and query parameters arrive as inputs (`id`, `category`, `item`, `returnUrl`), not through a router-store. Do not name an output after a native DOM event that bubbles (`search`, `change`, `input`...): the parent's listener also receives the DOM event.
- Services call relative URLs (`/api/...`) and never send a user id: the server knows the caller from the JWT or the guest cookie. In development, `proxy.conf.js` forwards `/api`, `/Upload`, `/openapi` and `/scalar` to the ASP.NET backend.
- The login token is read and written only by `services/token-storage.service.ts` (`TokenStorage`): a malformed or expired token counts as no token, and it builds the signed-in `User` from the JWT payload. `authTokenInterceptor` adds the Bearer header from it. `errorInterceptor` always passes the original `HttpErrorResponse` on; a 401 (except from `/api/login`) calls `AuthStore.expireSession()` (token removed, the cart, wishlist and orders stores empty themselves, back to login with a `returnUrl`; never a page reload), 403 and 5xx show a snackbar. Stores keep failures as `errorText(error)` (`shared/http-error.ts`), never the raw error. `returnUrl` goes through `safeReturnUrl` (`shared/return-url.ts`).
- `AuthStore` reads the stored token when it is created, so a valid token means signed in from the first render (there is no "not looked at yet" state). `AppComponent` has nothing to do; the nav bar creates the stores.
- State management uses NgRx SignalStore, one store per feature in `state/<feature>/<feature>.store.ts` (`AuthStore`, `BooksStore`, `CategoriesStore`, `SimilarBooksStore`, `RegisterStore`, `CartStore`, `WishlistStore`, `OrdersStore`), all `providedIn: "root"`; nothing is registered in `main.ts`. There is no classic NgRx (no `Store`, actions, reducers, effects or selectors).
  - A store is `withState` + `withCallState()` (`shared/with-call-state.ts`: `callState` is `"init" | "loading" | "loaded" | { error }`, with `loading()`, `loaded()` and `error()`) + `withComputed` + `withMethods`. Async methods are `rxMethod`s using `tapResponse` (from `@ngrx/operators`).
  - `AuthStore` is the session. It reads the stored token in `onInit`; `login`, `logout` and `expireSession` change it. It knows no other store: `CartStore`, `WishlistStore` and `OrdersStore` watch `auth.userId()` in an `effect` inside `withHooks` and reload or empty themselves (the cart also loads at start, for guests).
  - `BooksStore` (entities by `bookId`) and `CategoriesStore` fetch once per session; admin add, update and delete change the list in place. Checkout has no store: `CheckoutComponent` calls `CheckoutService`, then `cart.load()`.
- Routes: all pages except Home are lazy-loaded with `loadComponent`. `authGuard` (a `CanActivateFn`) protects checkout, myorders and wishlist; `adminGuard` (a `CanMatchFn`) protects `admin/books`, whose child routes are in `routes/admin.routes.ts`. Both read `AuthStore` (synchronously) and return `true` or a `UrlTree`: a guest goes to `/login?returnUrl=...`, a signed-in non-admin goes home.
- The price filter is a signal on the home page (the old `SubscriptionService` is gone).
- Path imports use the `src/app/...` form, resolved through `paths` in tsconfig (TypeScript 6 deprecates `baseUrl`). TypeScript is `strict`; models are interfaces; fonts and icons are self-hosted (`@fontsource/roboto`, `@fontsource/material-icons`), nothing is loaded from a CDN.
